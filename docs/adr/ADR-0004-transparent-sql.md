# ADR-0004: Transparent SQL Execution

- **Status:** Accepted
- **Date:** 2026-07-17

---

# Context

Most graphical database tools execute a large number of SQL statements behind the scenes.

These queries are typically hidden from the user.

As a result:

- DBAs cannot verify how metadata is collected.
- Performance problems are difficult to investigate.
- Optimizing or replacing internal queries is difficult.
- Trust in the application decreases because its behavior is opaque.

Since the target audience of `mydba` consists of experienced MySQL DBAs, hiding SQL execution is contrary to the philosophy of the project.

---

# Decision

Every SQL statement executed by `mydba` against the target server must be visible.

The application shall maintain a dedicated SQL log containing every statement it sends to the server.

This includes both user-initiated SQL and SQL generated internally by the application.

---

# Rationale

Transparency provides several benefits:

- Users understand exactly how information is retrieved.
- Metadata queries can be reviewed and optimized.
- Performance investigations become easier.
- Unexpected behavior can be diagnosed quickly.
- The application becomes easier to trust.

The SQL generated by `mydba` should never be treated as an implementation secret.

---

# Scope

The SQL log includes:

- Metadata queries
- Object Browser queries
- Administration queries
- Monitoring queries
- Export queries
- Dependency analysis queries
- User SQL executed from the SQL Workspace

In short, **every SQL statement sent to the database**.

---

# SQL Log Contents

The SQL log contains only SQL-related information.

Each entry should include:

- Timestamp
- SQL statement
- Execution duration (when available)

No application diagnostics or unrelated messages should appear in the SQL log.

---

# Separate Application Log

General application logging is intentionally kept separate.

The application log records items such as:

- Startup and shutdown
- Internal exceptions
- Plugin loading
- Configuration errors
- UI events
- Debug information

Mixing SQL and application events in a single log would reduce readability.

---

# User Visibility

The SQL log is intended for:

- Learning how `mydba` works
- Troubleshooting
- Performance analysis
- Future optimization

It is not intended to function as an audit log.

---

# Security Considerations

The SQL log must not expose sensitive information unnecessarily.

In particular:

- Passwords must never be written to the SQL log.
- Authentication credentials must never be logged.
- Sensitive connection details should be handled carefully.

If future features execute SQL containing secrets, those values should be masked before logging.

---

# Performance Impact

Writing executed SQL to a log file introduces minimal overhead compared to the execution time of the queries themselves.

The transparency gained significantly outweighs the small performance cost.

---

# Alternatives Considered

## Hidden Internal SQL

Rejected.

Hidden behavior makes debugging difficult and prevents users from understanding how metadata is obtained.

---

## Optional SQL Logging

Rejected.

Because SQL transparency is a core design principle, logging should be enabled by default.

Future versions may allow disabling it for specific use cases, but transparency remains the default behavior.

---

## Combined SQL and Application Log

Rejected.

SQL and application diagnostics serve different audiences and purposes.

Keeping them separate makes both logs easier to read and analyze.

---

# Consequences

Every component of `mydba` must execute SQL through a common database layer that records the statement before or after execution.

This ensures consistent behavior across the application and avoids accidental omissions.

Developers introducing new features must ensure that all SQL passes through this shared execution path.

---

# Future Considerations

Future enhancements may include:

- Log rotation
- Configurable log locations
- Session identifiers
- Optional execution statistics
- SQL formatting for improved readability

These additions should preserve the central principle:

> Every SQL statement executed by `mydba` should be visible to the user.
